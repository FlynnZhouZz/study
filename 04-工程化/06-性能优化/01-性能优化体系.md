# 前端性能优化体系

性能优化最大的坑是**凭感觉优化**。正确顺序永远是：**定指标 → 采集基线 → 定位瓶颈 → 优化 → 对比验证**。

本文覆盖 Web 与 RN 两条线。理论依据见 [浏览器渲染原理](../../01-计算机基础/02-浏览器原理/README.md)。

## 一、先定指标

Core Web Vitals 是业界共识的三个维度：

| 指标 | 含义 | 良好阈值 | 反映什么 |
|------|------|----------|----------|
| **LCP** | 最大内容绘制 | < 2.5s | 加载性能：主要内容多久可见 |
| **INP** | 交互到下次绘制 | < 200ms | 交互性能：点击后多久有响应 |
| **CLS** | 累积布局偏移 | < 0.1 | 视觉稳定性：内容是否乱跳 |

辅助指标：TTFB（< 800ms，服务端响应）、FCP（首次绘制）、TBT（主线程阻塞总时长）。

> INP 在 2024 年 3 月正式取代 FID。面试如果还在说 FID，说明资料是旧的。

**采集方式**（线上真实数据优于实验室数据）：

```ts
import { onLCP, onINP, onCLS } from "web-vitals";

onLCP((m) => report("lcp", m.value));
onINP((m) => report("inp", m.value));
onCLS((m) => report("cls", m.value));
```

实验室数据用 Lighthouse / Performance 面板，用于复现和定位。

## 二、加载性能（LCP）

LCP 慢只有四个原因，按排查顺序：

### 1. 服务端响应慢（TTFB 高）

- 加 CDN、开 HTTP/2 或 HTTP/3
- 接口做缓存（`Cache-Control`、ETag）
- 减少重定向链、优化数据库慢查询

### 2. 资源体积大

| 手段 | 收益 |
|------|------|
| 代码分割（路由级 `import()`） | 首屏只加载当前路由 |
| Tree shaking | 删掉未使用代码，见 [构建工具](../02-构建工具/01-构建工具原理与选型.md) |
| 图片用 webp/avif + `srcset` | 通常占页面体积 60%+ |
| 字体子集化 + `font-display: swap` | 避免字体阻塞文本渲染 |
| gzip / brotli | 文本资源普遍减 70% |

### 3. 关键资源被阻塞

```html
<!-- 非关键 JS 延后 -->
<script src="analytics.js" defer></script>

<!-- 关键 CSS 内联，其余异步 -->
<link rel="preload" href="/critical.css" as="style" />

<!-- 提前建连，省掉 DNS + TCP + TLS 的三次往返 -->
<link rel="preconnect" href="https://api.example.com" crossorigin />
<link rel="dns-prefetch" href="https://cdn.example.com" />
```

**LCP 元素本身要优先**：如果 LCP 是首屏大图，给它加 `fetchpriority="high"`，别用 `loading="lazy"`（lazy 会推迟 LCP）。

### 4. 渲染路径长

- SSR / SSG 让 HTML 直达，减少客户端渲染等待
- 流式渲染（React `renderToPipeableStream`）让首屏更早吐出
- 骨架屏改善**感知**性能（不改善真实指标，但要诚实标注这一点）

## 三、交互性能（INP）

INP 差的根因通常是**主线程被长任务占住**。判定标准：单次任务超过 50ms 即为长任务。

**定位**：Performance 面板看主线程火焰图，找最长的黄色块；或用 `PerformanceObserver` 线上采集：

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) report("longtask", entry.duration);
  }
}).observe({ type: "longtask", buffered: true });
```

**优化手段**：

1. **拆分长任务**：把大循环切成小片，用 `scheduler.yield()`（或 `setTimeout` 兜底）让出主线程。

```ts
async function processInChunks(items: string[]) {
  for (let i = 0; i < items.length; i++) {
    handle(items[i]);
    if (i % 50 === 49) await scheduler.yield(); // 让浏览器有机会响应输入
  }
}
```

2. **减少不必要的渲染**：React 场景见 [常用的性能优化操作](../../03-框架与跨端/01-react/10-常用性能优化操作.md)。
3. **重活挪出主线程**：Web Worker 处理解析、加密、大数组计算。
4. **避免强制同步布局**：读写分离，不要在循环里交替读 `offsetHeight` 和写 `style`。

```js
// ✗ 每次都强制重排
for (const el of els) { el.style.width = el.offsetWidth + 10 + "px"; }

// ✓ 先批量读，再批量写
const widths = els.map((el) => el.offsetWidth);
els.forEach((el, i) => { el.style.width = widths[i] + 10 + "px"; });
```

## 四、渲染稳定性（CLS）

- 图片、视频、iframe 必须写死宽高或 `aspect-ratio`
- 广告位、动态插入的横幅预留占位
- 字体加载导致的文本重排：用 `size-adjust` 匹配回退字体度量
- 不要用 `top`/`left` 做动画，用 `transform`（合成层，不触发布局）

## 五、内存

**泄漏的典型来源**：未解绑的事件监听、未清理的定时器、闭包持有大对象、Detached DOM（DOM 删了但 JS 还引用着）。

**排查**：DevTools Memory 面板拍两次堆快照（操作前 / 操作后），对比 `Detached HTMLElement` 与不断增长的构造函数实例数。

```ts
// 组件卸载时务必清理
useEffect(() => {
  const id = setInterval(tick, 1000);
  window.addEventListener("resize", onResize);
  return () => {
    clearInterval(id);
    window.removeEventListener("resize", onResize);
  };
}, []);
```

## 六、RN 性能（另一套指标体系）

RN 没有 LCP/INP，关注点是**启动、滚动、交互**。

| 指标 | 含义 | 优化方向 |
|------|------|----------|
| 冷启动时间 | 进程冷启到首屏可交互 | 减少 native 初始化、Hermes 预编译、拆包 |
| TTI | 可交互时间 | 延后非关键 JS 执行、首屏组件精简 |
| 列表 FPS | 滚动流畅度 | `FlatList` 优化、避免内联函数、图片尺寸匹配 |
| 包体积 | 安装包大小 | 资源裁剪、按需加载 |

详细实践见 [优化 APP 启动速度](../../03-框架与跨端/03-react-native/04-优化APP启动速度.md)。核心思路与 Web 一致：**先测量分段耗时，再针对最长的一段优化**。

## 七、优化方法论（面试最容易被追问的部分）

1. **不要优化没有被测量的问题**。先有基线，再谈收益。
2. **一次只改一个变量**，否则无法归因。
3. **区分真实性能与感知性能**，汇报时说清是哪一个。
4. **收益要用数据说话**：优化前后各跑 3 次取中位数，说明采集环境。
5. **关注长尾**：P75 才是 Core Web Vitals 的评估口径，平均值会掩盖慢用户。

## 八、常见追问

- 白屏时间怎么测？（FCP、首屏模块加载完成、`performance.mark` 打点）
- 首屏优化你做过哪些？效果如何量化？
- `preload` / `prefetch` / `preconnect` / `dns-prefetch` 的区别？
- 为什么说"减少重排"比"减少重绘"更重要？（重排会重建布局树，代价高一个量级）
